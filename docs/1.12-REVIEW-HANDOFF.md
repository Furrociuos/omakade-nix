## 4. Journal, session identity and interval design

### Session identity

A session now gets a stable key before its first database write. `SessionRecorder` mints a UUID
when it creates the session and passes it to `SessionDatabase::beginSession`, which writes it
with `INSERT OR IGNORE` and, on a key collision, resolves the existing row id instead of
failing. A close uses the same key through `insertClosedSession` and `endSessionByKey`. Row ids
are never used as cross-database identity.

### Journal format and location

- Location: `<library database path>.journal`, so `$XDG_DATA_HOME/omakade/library.sqlite3.journal`.
  The parent directory is created and the file is written owner-read/write only (`0600`).
- Framing: header `OMKJRNL1\n`, then records of a 4 byte big endian payload length, the UTF-8
  JSON payload, and a 4 byte big endian CRC32 of the payload. Payloads carry `v` (format
  version 1). An unknown version is skipped, not guessed. A record over 64 KiB is corrupt.
- Kinds: `op` (a durable session operation: key, game, source, start, end, seconds, pid,
  procStart, game generation, global generation) and `ack` (a committed key).

### Write and acknowledge order

1. The operation is appended to the journal and `fdatasync`ed before it is acknowledged
   anywhere else. Only then is it in the in-memory retry queue as durable work.
2. Replay applies each pending operation with `insertClosedSession` under its stable key, which
   is idempotent: a session that already has a row is closed by key, and a session that never
   had one is inserted. After the writes commit, the committed keys are compacted out of the
   journal. A crash between the commit and the acknowledgment replays the same key as a no-op.

### Capacity and failure policy

- Hard caps: 512 live records or 256 KiB, whichever is reached first. At the cap the journal
  refuses new records, sets a capacity flag, and never evicts an accepted record. The daemon
  logs the condition once through `takeJournalCapacityWarning` and notifies
  `tracking-journal-full`; the condition clears when the journal drains.
- Replay and retry share the existing flush interval and only run when work is pending, so a
  lasting failure backs off instead of spinning. There is no new job service.
- The in-memory retry queue keeps its original 64 entry cap. An entry past the cap is now
  delayed, not lost, because the durable copy is in the journal. This preserves the existing
  `pendingClosesAreBoundedUnderAStorageFailure` baseline.
- A corrupt or truncated journal is renamed once to `<path>.corrupt` and replaced with a fresh
  file, so one bad file cannot poison every later startup. The corrupt copy is kept for
  diagnostics. No private data is printed.
- A full or read-only filesystem defeats the database and the journal together. Zero loss is
  not promised when no durable destination accepts a write; this is stated in the design note,
  the changelog and the coverage table.

### Deletion, restore and downgrade

- A per-game generation counter and a global generation counter live in
  `session_tombstones` and `session_journal_state`. Deleting one session, clearing a game's
  history, or clearing a game that only had a pending record bumps the game generation; a
  database replacement or restore is expected to bump the global generation. Journal records
  carry both generations and replay drops records older than the current values, so removed
  history cannot be resurrected.
- Schema changes are additive and idempotent in `ensureSchema`: the two new tables plus the
  existing `session_key` column and index. No existing table or row is rewritten.
- Downgrade: an older binary sharing the database ignores the new tables and the adjacent
  journal, and the session row shape is unchanged, so it keeps working. An old binary does not
  read a 1.12 journal and is not expected to resume new work. This is a stated boundary.

## 7. Privacy, security, remaining loss windows and limitations

- Session records hold game paths, which are private. The journal is owner-only (`0600`) and
  sits inside the data directory. No session content is written to public logs; the daemon logs
  only the condition (corruption or capacity), not records.
- Journal input is validated for length, framing, CRC, version, key size, path size and
  non-negative totals. Unknown versions are skipped. A malformed file is preserved once and
  replaced.
- Remaining loss windows: up to one flush interval (30 s) of an open session's duration lives
  only in the database row, not the journal, by design; the journal carries completed
  operations. If both the database and the journal storage are unwritable (a full or read-only
  filesystem), accepted work is not durable. The in-memory queue still holds the most recent
  64 entries for in-run retry.
- The global generation counter is bumped only by the code paths wired here (per-game deletion).
  Backup restore and database replacement are not yet wired to `bumpJournalGeneration`, so an
  old journal record could survive a restore until that is connected. This is a known gap, not
  a claimed protection.
- Interval support (Scope B) is absent, so the journal carries no interval records.
- Downgrade to an older binary is safe for the database shape but the old binary will not read
  the journal; a 1.12 journal left behind is ignored by the old binary.

with new regressions. The reviewed commit `45c9cdd` is superseded.

| Finding | Fix |
| --- | --- |
| R1 same-process retry resurrects cleared history | The in-memory retry now calls the same transactional guard as replay, so a live clear drops it. New test `sameRecorderRetryDoesNotResurrectClearedHistory`. |
| R2 one deletion invalidates other pending sessions | A single deletion tombstones only that session's key; a whole-game clear moves the clear epoch. New test `singleDeletionKeepsOtherPendingSessions`. |
| R3 torn append excludes earlier valid records | `open` truncates back to the verified prefix and only quarantines interior damage. New test `tornAppendKeepsVerifiedPrefix`. |
| R4 restore not isolated from an old journal | Records carry a random database incarnation; a replace restore writes a new one (`BackupDatabase.cpp`). New test `replayRejectsRecordsFromAnotherIncarnation`. |
| R5 journal-only records do not drain | Ordinary polling drains the journal beyond the memory cap (`drainJournal`). New test `journalDrainsBeyondMemoryCapWithoutRestart`. |
| R6 refused active sessions stay volatile | An active session whose insert or progress update is refused is checkpointed once per flush interval and replayed as an open row, then reconciled. New test `activeRefusedSessionIsCheckpointed`. |
| R7 `beginSession` can return another session's row | The stable key is resolved by `numRowsAffected`, not `lastInsertId`. New test `stableSessionKeyResolvesCorrectRow`. |
| R8 journal status not connected to the UI | `SingleInstance` handles the journal notifications, `PlaySessionStore` exposes `journalPending` and `journalWarning` read from the journal file, and Settings shows a persistent warning. |

## 13. Addendum 3: response to the third review pass

The third pass found three more faults. The first is the identity limitation Addendum 2
disclosed, now demonstrated to violate restore isolation, so it was not a safe limit to ship.
All three are fixed in commit `5d931dd`, each with a regression. The reviewed commit `f8b93c9`

| Finding | Fix |
| --- | --- |
| A replace restore could resurrect old history through an anonymous record | An anonymous record is now dropped when the database has any identity; the recorder stamps from the identity it last saw so records usually carry one; and a replace restore removes the journal, so the boundary does not depend on the record carrying one. | A delayed recovery left a dead session open and unremovable | A recovered active session whose process has exited is closed at its last observed time, never below the row's existing progress, so it can be deleted. New test `delayedRecoveryClosesDeadSession`. |
