# Durable recovery boundaries

The session key identifies one recording across failed inserts, checkpoints and retries.
When replay is delayed, the recorder reserves that original key and observed progress in
memory before another matched poll can create a new identity. Once storage recovers,
adoption merges progress without moving the elapsed-clock mark or discarding observations.
Retries use the latest durable operation for a key, not an older queued checkpoint.

Replay merges seconds and heartbeat monotonically. Closing a checkpoint-derived session
uses the latest stored heartbeat as well as the checkpoint boundary. Required closes are
transactional with replay and remain retryable on failure. A live process is adopted only
for the same process-start identity and game.

A journal has a durable owner token, bound to the current database. Anonymous operations
are accepted only with matching ownership. Replace installs a new owner in the same
transaction as the new database incarnation, so retained pre-restore journal records are
rejected even if filesystem cleanup was interrupted. A recorder may bind an empty journal
to the new database owner only after durably writing the empty journal. It then durably
replaces the owner sidecar. The old owner therefore cannot acquire new authority while
old anonymous records remain on disk. New recording outages after restore retain the new
owner relationship even when the initial database read fails.

Journal replacement writes and syncs a same-directory temporary file, renames it, then
syncs the target and parent directory. Failure is not durable acknowledgement. At process
termination around rename, the retained journal must be a complete old or new version.
Physical power-loss and real disk-full validation remain separate acceptance boundaries.

This describes the durability work only. Activity intervals, additional emulator support,
attribution adapters and repair workflows remain outside this phase.
