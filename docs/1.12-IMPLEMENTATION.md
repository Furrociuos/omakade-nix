## Scope A: durable recording and recovery

### Failure model

The recorder already tracks sessions in memory and writes them to the shared library
database. Two failure modes lose recorded play today:

- Storage refuses an insert or a close. The operation is held in a 64 entry in-memory
  queue and retried, but the oldest entries are dropped past the cap and the whole queue
  is lost when the recorder exits.
- The recorder process is killed between a successful database write and forgetting it,
  or before a queued write is persisted anywhere.

The durable journal removes the second mode for accepted work and raises the first from
"lost" to "delayed, with an explicit capacity warning". It cannot promise zero loss when
no durable destination accepts a write: a full or read-only filesystem defeats the database
and the journal together, and that is stated plainly rather than hidden.

### Storage location and permissions

- Journal path: `<library database path>.journal`, so
  `$XDG_DATA_HOME/omakade/library.sqlite3.journal` by default.
- The parent directory is created mode `0700` and the journal file mode `0600`, owner only.
  Session records contain game paths, which are private.
- The journal is a sibling of the database, so it survives database replacement and is
  removed with the same data directory. It never lives under `/tmp`.

### Record format and version

Binary framing, little surface area, easy to validate:

- File header: the ASCII bytes `OMKJRNL1\n`. A file without it is treated as corrupt.
- Owner sidecar: `<journal>.owner`, created durably before the first accepted record. It
  holds a random token that binds this journal instance to a database identity.
- Each record: 4 byte big endian payload length, then the payload, then 4 byte big endian
  CRC32 of the payload.
- Payload: compact UTF-8 JSON with a `v` version field. Unknown versions are skipped, not
  guessed. A record longer than the per-record cap is corrupt.

Record kinds:

- `op`: a durable session operation. Fields: `key` (stable session key), `game`, `source`,
  `start`, `end`, `seconds`, `pid`, `proc`, `obs` (the wall time the state was observed),
  `inc` (database incarnation), `gep` (the game's clear epoch when written), and `open` (true
  for an active-session checkpoint, false for a finished session).
- `ack`: `key`, written after the matching database write commits.

Replay keeps the latest `op` per key in file order and drops any key that has an `ack` after
it. The journal itself does not decide staleness; the database guard below does, inside the
write transaction, so a single-session deletion cannot drop an unrelated pending session.

On open, a file whose final append was torn by a crash is truncated back to its verified
prefix, so records that were already accepted and fsynced still replay. Only interior damage
(a complete frame with a bad checksum, or a bad header) is quarantined, once, to a `.corrupt`
copy.

### Durable ordering

1. Give the session a stable identity before its first database write: the recorder mints
   the `session_key` when the session starts and reuses it for every later write, instead
   of letting the database assign one at insert time. Database row ids are never used as
   cross database identity.
2. When an operation cannot be written, persist it to the journal and synchronize its file
   data and metadata before acknowledging it anywhere else. Only then is it eligible to be
   reported as pending. Creating the journal and owner sidecar also synchronizes the parent
   directory.
3. On replay, apply the operation in a database transaction, commit, then append the `ack`
   and compact. A crash between commit and ack replays the same stable key, and the insert
   is idempotent on `session_key`, so no session, total, interval or imported credit is
   duplicated by replay.
4. Replacing the journal writes a same-directory temporary file, fdatasyncs and fsyncs it,
   atomically renames it, fsyncs the renamed file, and fsyncs the parent directory. Any
   failed step makes the journal unavailable and returns failure; the old complete file or
   the new complete file remains, never a half-acknowledged replacement.

### Capacity and backoff

- Hard caps: 512 live records or 256 KiB, whichever is reached first. The cap bounds both
  disk use and per poll replay work. One record per key is kept, so a newer operation for a
  key replaces its pending record; repeated checkpoints for one long session neither grow the
  file nor count toward the entry cap.
- The status probe mirrors the same caps, including the byte cap, so a journal full by size
  still raises the persistent warning.
- At the cap the journal stops accepting new records and sets an explicit capacity flag.
  Accepted records are never silently evicted. The recorder reports a concise, persistent
  status so the interface can warn through the existing recorder surface.
- Replay and retry are paced by the existing flush interval and only run while entries are
  pending; a lasting failure backs off instead of spinning. Pending records past the 64 entry
  in-memory queue are drained from the journal during ordinary polling, so storage recovery
  does not need a recorder restart. Each pass is bounded (512 at start, 256 while running).

### Deletion, restore and identity

Identity is per record and validated at write time, inside the same transaction as the
write, so a deletion by the interface cannot race the recorder into resurrecting history:

- The database carries a random incarnation, created on first use and rewritten after a
  replace restore. A journal record stores the incarnation it was written under; a record
  from a different incarnation is stale. A fresh random value is used rather than a counter
  because a counter restored from an old backup cannot establish identity across an
  arbitrary replacement.
- Clearing a whole game's history moves a per-game clear epoch, so that game's pending
  records are stale.
- Deleting one session tombstones that session's key only, so a different pending session
  for the same game stays valid. A game-wide clear is the only operation that invalidates
  every record for a game.
- Every replay path uses the same guard: the in-memory retry of a still-running recorder and
  the restart replay both call `SessionDatabase::replayClosedSession` or
  `replayOpenSession`, which run the identity, clear-epoch and tombstone checks in the write
  transaction. A stale operation is dropped and compacted, an error is retried.
- Unknown identity is a distinct state, not either "owned" or "stale". The journal owner
  token is bound to the database incarnation when both can be read. An anonymous record is
  replayed only if that durable binding proves it belongs to the current database; otherwise
  it remains retryable while ownership is unresolved, and is stale when a restore or replace
  has provably invalidated the prior binding. A replace restore rotates the identity, marks
  the old owner invalid, and removes both journal files. The recorder still stamps records
  from identity it last saw, so a record accepted during a lock normally carries one anyway.

### Migration and rollback

- The identity, clear-epoch and tombstone tables are created idempotently by
  `SessionDatabase::ensureSchema`. The `session_key` column and its unique index already
  exist from 1.11; 1.12 adds the stable-key write path on top.
- An older binary that shares the same database ignores the new tables and journal file and
  keeps working, because the session row shape is unchanged. A downgrade cannot read a
  journal written by 1.12, and does not try to: the journal is an adjacent file, not a
  schema the old code opens. The review handoff states this compatibility boundary
  explicitly instead of implying an old binary can safely resume new work.

### What survives what

- Crash tail: an active session is checkpointed to the journal once per flush interval while
  the database refuses its insert or progress update, so a killed recorder loses at most one
  interval (30 s) instead of the whole session. A completed session is journaled on close,
  so its tail is one poll plus one fsync.
- Failed insert: the session is tracked with its original start and checkpoints, then
  journaled and replayed.
- Failed progress update: the row keeps its last flushed seconds and the checkpoint carries
  the observed total, replayed into the row when storage recovers.
- Failed close: the close is journaled and replayed.
- Failed active checkpoint: retried as an open session, never written as a closed one, because
  clamping an open record's end to its start would record a zero-length session.
- Recovered heartbeat: a replayed checkpoint keeps the wall time it was observed at, and never
  lowers the recorded seconds an already-written row carries, so a restart cannot move a
  session forward to the replay instant or shrink its total.
- A failed identity read (a locked or busy database) is retried, not treated as a replaced
  database, so a temporary outage cannot permanently discard an accepted record.
- A recovered active session whose recorded process has exited is closed at its last observed
  time, never at the replay instant and never below the progress the row already carries. A
  delayed replay therefore does not leave an open row that history deletion refuses to remove.
- A delayed replay reconciles with current process identity. A survivor running the same game
  is adopted under the original stable key; one running another game closes the old row at
  its observation boundary and the normal poll opens the new game. This applies to both the
  bounded memory retry queue and journal-only draining.
- A successful open-row replay does not acknowledge a required final close. Dead or changed
  processes close in the same transaction where practical; a failed close keeps the original
  boundary, never lowers progress, and remains retryable until the close commits.
- Orderly shutdown: active sessions are closed and journaled as closes, then replayed.
- Records past the in-memory retry cap are drained from the journal during ordinary polling,
  not only at the next recorder start.

## Scope B: observed activity intervals (design only)

Not implemented. The intended design keeps monotonic time authoritative for billed
duration and records observed active and paused spans with a completeness marker. Legacy
aggregate rows keep their labelled proportional estimate. Because it is unimplemented, no
schema or Stats change is present in this branch, and the review handoff says so.

## Scopes C to F

Not implemented. The handoff requires verified upstream contracts before each source, and
those have not been established in this branch. Writing a scanner from memory would violate
the explicit instruction not to guess paths, arguments or formats, so no source stub is
added. The review handoff records this as the concrete remaining scope.
