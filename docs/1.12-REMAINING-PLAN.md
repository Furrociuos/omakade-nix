## Part B: observed activity intervals

### User outcome

Time of day and calendar allocation follow when play actually happened, so a session that ran
from 22:00 to 01:00 is credited as night plus the small hours on observed evidence rather than
by spreading the total evenly across the span.

### What it is honestly built on

- Billed seconds stay monotonic and authoritative. Nothing here changes what a session is
  worth; it changes where in the calendar that worth is placed.
- The observable pause today is the recorder's focus predicate, which is off by default and
  off in the maintainer's config. Suspend is the other observable gap, and no session in the
  database contains one yet. The feature is a precision improvement whose input the current
  configuration and data do not produce.
- Legacy rows have only an aggregate span, so their proportional placement stays and keeps its
  label. The honest mixed-history answer is to allocate observed spans where intervals exist,
  and to say plainly which sessions were estimated.

### Design

Schema, additive and idempotent in `SessionDatabase::ensureSchema`:

- `session_intervals(session_key TEXT, seq INTEGER, wall_start INTEGER, wall_end INTEGER,
  billed_seconds INTEGER, kind TEXT, PRIMARY KEY(session_key, seq))`. One row per contiguous
  run of billed time. `sum(billed_seconds)` over a session's rows equals the session's
  `seconds`, which is the invariant every test should assert first.
- `play_sessions` gains a provenance column written once at close: `observed` when the session
  was recorded with intervals, `aggregate` for everything older. Existing rows default to
  `aggregate`, which reproduces today's display exactly.

Wall mapping policy, which is the part that has teeth:

- Each interval carries the wall time of the poll that opened it and of the poll that closed
  it, taken at observation. No local-time arithmetic happens at write time, so timezone and
  DST changes cannot move a stored span.
- Monotonic time decides billing. A suspend appears as a wall span wider than its billed
  seconds, and the allocator spends only the billed seconds inside it.
- A wall clock that steps backwards can produce a span whose billed seconds exceed its wall
  span. The span keeps its anchors, the excess is billed at the opening anchor, and the
  session is marked approximate rather than dropped. A wall-clock correction must never
  manufacture hours, which means the allocator clips to `billed_seconds` and never to the wall
  span.
- Unknown focus stays unknown. With no focus evidence the recorder bills continuously exactly
  as it does today, and no interval is labelled paused.

Allocation in `PlayStats`:

- Read intervals where the session has them, and place each interval's billed seconds across
  the hour and weekday slices it overlaps, clipped to the requested period. The existing
  epoch-timeline slice loop, which preserves a repeated DST hour, is the allocator; only its
  input changes from one span per session to one span per interval.
- Keep the proportional path for aggregate sessions, and keep `estimatedTiming` set when any
  session in the period used it, so the window note keeps naming the estimate.
- Concurrent sessions: two games recorded at once produce overlapping intervals, so hourly
  totals can exceed the period total, exactly as they can today. That stays as it is and is
  stated, rather than changing session totals incidentally.

### Slices

1. **B1 Schema and recorder persistence.** Interval rows, provenance column, writes on pause,
   resume, checkpoint and close, and the sum invariant.
2. **B2 Allocation.** `PlayStats` reads intervals, keeps the proportional path, and asserts
   the per-hour sum and the period total together.
3. **B3 Deletion, restore and replay.** Intervals are removed with their session in
   `deleteSession`, `deleteSessionsForPaths` and clear-all, and a journaled replay writes them
   inside the same transaction as the row so no orphan interval can exist. Tombstone and
   incarnation checks are unchanged.
4. **B4 Labels and export parity.** The screen and the PNG card read one period and one total,
   and both say when a period contains estimated sessions.
5. **B5 Tests.** Pause across midnight and New Year, leap day, DST transitions, a timezone
   change, a backwards wall-clock step, suspend and resume, restart while paused, a partial
   interval checkpoint, mixed legacy and new rows, linked installations, deletion, restore,
   replay and export parity.

### Acceptance journey

Turn pause-on-unfocus on, play a session that loses and regains focus, and confirm the paused
span is a gap in the hourly split and the session total is unchanged. Suspend mid-session and
confirm no phantom hours. Restart the recorder while a game is paused and confirm the session
survives with its observed spans. Delete the session and confirm its intervals go with it.

### Out of scope

In-game pause menu detection, a timeline editor, new analytics views, and pause support on
compositors beyond the existing focus-evidence contract.

### Contract decisions already made

- Discovery is bounded in all three: documented config roots plus explicit user roots, no home
  directory crawl, depth 1 unless the emulator's own recursion setting says otherwise.
- Rejections are by evidence, not by guesswork. RPCS3: refuse anything under `dev_flash`,
  refuse `dev_hdd0` paths except `game/`, refuse categories `GD`, `2D`, `SD`, `MS`, media apps,
  `HM`, `/OS`, and accept `DG`, `HG`, `1P`, `2P`, `2G`, `PP`, `MN`, `PE`. melonDS: reject by
  extension and header (`IsHomebrew`, `IsDSiWare`, missing gamecode, `UnitCode`) and exclude
  cheats, states and save files by construction. PPSSPP has typed rejection messages for save
  data, save states, PS1 EBOOTs and UMD Video, which we mirror.
- BIOS, firmware and keys are never library entries. melonDS FreeBIOS means a missing BIOS is
  not an error to surface.
- Save states are never in-game saves, and melonDS `RelocSRAM` re-points the battery save at
  `<state>.sav`, so that file has to be excluded when the setting is on.
- A shared save container is labelled shared. That is `PSP/SAVEDATA`, the melonDS ROM folder
  (which also holds GBA slot-2 saves), and the RPCS3 `savedata` tree.
- All three launch through structured argv with no shell evaluation.

## Part D: bounded attribution beyond command lines and titles

### User outcome

When a game is started from inside an emulator's own file picker, history names the game that
was actually played instead of the previous one under the same process.

### Evidence available, per emulator

From `attribution-evidence.md`, which quotes the tagged source for each row:

| Emulator | Current-session artifact | Verdict |
| --- | --- | --- |
| Dolphin 2606 | `TimePlayed.ini`, rewritten by a dedicated thread every 30 s while running, atomic temp-and-rename, keyed by disc id, on by default | Admissible. Best contract available |
| PCSX2 2.9.34 | `logs/emulog.txt`, truncated per run, flushed per line, `Disc changed to <file>` plus `Name`, `Serial`, `Version`, `CRC` per boot | Admissible, second choice |
| RPCS3 v0.0.42 | `RPCS3.log` per-boot line with the full path and title id | Admissible later, once flush latency is verified on a real install |
| PPSSPP v1.20.4 | `[Recent]` paths and `[PlayTime]`, written at shutdown | Recents only, rejected |
| melonDS 1.1 | `RecentROM`, written at exit | Recents only, rejected |
| RetroArch 1.22.2 | `content_history.lpl` with no timestamps, and `.lrtl` written at content close | Rejected |

PCSX2's `inis/playtime.dat` and PPSSPP's `[PlayTime]` are historical records and must stay out
of the session path. Omakade already parses `playtime.dat` for imports; that use is correct
and unrelated.

### Design

- A small read-only adapter interface: given a live process identity (`pid`, `procStart`, the
  matched profile) and the library's known identities for that source, return an attribution
  with a confidence kind. Three evidence kinds stay separate: command line (strong), adapter
  (session-verified), window title (weak). The strongest present kind decides, and the adapter
  never overwrites a command-line match for the same process, mirroring what
  `ProcessMatcher::matchWithWindowTitles()` already does for titles.
- Dolphin contract, the one to implement first: at first sight of a Dolphin process, snapshot
  the key-to-value map in `TimePlayed.ini` plus the file's identity. Valid attribution needs
  all of: the process alive, the file identity unchanged (or a fresh baseline if it was
  replaced), `now - mtime` inside a 60 s freshness window, exactly one key whose value
  increased since the baseline, that key mapping to exactly one library game, and no strong
  command-line match for that pid. Anything else keeps the previous attribution.
- A paused-but-alive Dolphin stops writing, so a stale mtime is not "no game". It keeps the
  last confirmed attribution and carries a staleness flag rather than silently ending a
  session.
- Reads are bounded: one `stat` per poll per process, a full parse only when mtime or size
  changed, offsets remembered, and truncation or inode change treated as a new session.
- Attribution confidence is separate from authority. Only a verified process identity may
  grant stop authority, so an adapter- or title-derived attribution must not make a shared
  emulator process killable.

### Slices

1. **D1 Contract and interface.** The adapter interface, evidence precedence, the confidence
   kinds, and tests that a weak kind cannot overwrite a strong one.
2. **D2 Dolphin adapter.** Baseline, freshness, single-key increase, staleness flag, bounded
   reads, and the rejection cases.
3. **D3 PCSX2 adapter.** Bounded tail of `emulog.txt`, truncation and inode detection, a
   serial identity matched against the source's own game ids, and an explicit "source
   unavailable" state when the user has turned file logging off.
4. **D4 Surfacing.** Recorder status and `RECORDING-COVERAGE` say which sources have verified
   attribution and which fall back to command line and title matching, including the honest
   statement that PPSSPP, melonDS and RetroArch still cannot prove the loaded game.

### Status

D1 and D2 are implemented: the adapter contract in `src/tracking/AttributionAdapter.{h,cpp}`, the
Dolphin record adapter, the three-kind precedence in `ProcessMatcher::matchWithAttribution`, the
identity lookup the adapter resolves through (`SessionTitleIndex::pathForGameId`, built from each
source cache's own `game_id`), and the daemon wiring that offers every emulator process to the
adapter. Regression coverage is in `tests/CoreTests.cpp` as `attributionOutranksWindowTitles` and
`dolphinTimePlayedAttributesTheLoadedGame`. The stop path is untouched and still reads
command-line evidence only (`GameStop` calls `ProcessMatcher::match`), so adapter evidence cannot
authorize a signal. D3, and the part of D4 that surfaces per-source confidence in the interface,
are not started. Nothing here has been verified against a real Dolphin session yet: the fixtures
write the record the way Dolphin does, but only the maintainer's own play can confirm the timing.

### Tests

No-game menu, stale recents, two games with the same title, a log rotation and truncation, a
game change inside one process, a wrapper or Flatpak root, a recorder restart, paused-but-alive
staleness, the baseline requirement, a synthetic two-key increase treated as ambiguous, and an
adapter whose file disappears mid-session.

### Acceptance

Requires a real Dolphin session with a real disc change, because every automated fixture
stands in for a file the emulator writes. The maintainer's `TimePlayed.ini` already holds two
real disc ids, so a GameCube disc change is the cheapest honest acceptance available.

## Part E: repair actions and restrained usability

### User outcome

A game that will not play says why in its own words, and offers the single action that fixes
that reason.

### What exists today

Inventory from the tree, before adding anything:

- Reasons: `identification`, `artwork`, `unavailable`, `duplicates`. `unavailable` is one
  condition derived from one bit, whether the entry reports as installed.
- Actions: correct identity, choose artwork, launch setup and link, undo identity, undo
  artwork, previous, next and skip, retry this game, select for retry, retry up to 100
  selected, stop retry, with a saved review position.
- Path repair does not exist in any form.
- Review position, selection and the undo checkpoints already persist across restart.

### Reason taxonomy

Each state gets one action, and no action that cannot work.

| State | Evidence today | Action | Must not offer |
| --- | --- | --- | --- |
| Moved or missing game file | the recorded path no longer exists | choose a replacement path, with a preview | a silent relink, or reassigning history and saves to another game |
| Disconnected storage | the path's root is absent while sibling entries under it are too | name the missing root and offer retry once it is back | deleting or hiding the entries |
| Unavailable runtime or core | the emulator or libretro core for this game is not resolvable | choose an installed runtime, or open launch setup | installing anything on the user's behalf |
| Failed scan or authentication | the source reported an error, not a missing game | retry that source, with its error text shown | mislabelling it as a bad match |
| Uncertain metadata | no confirmed catalog identity | the existing identity flow | treating a provider outage as a bad match |
| Duplicate suggestion | the existing same-system title count | link or keep separate | merging or deleting on title evidence |

### Path repair design

- A preview is mandatory: old path to new path, the identity that will be kept, and what will
  not be touched. History, saves, organization and overrides follow the game, not the path, so
  the preview has to say that.
- Reconciliation is deliberate: a replacement is accepted only when the user picks it, and a
  file whose identity contradicts the recorded one is refused with the reason, rather than
  silently reassigned.
- The existing artwork and identity undo stays coherent with a path change, so undoing a
  correction after a repair does not resurrect a stale path.

### Retry scoping

Retrying one entry must not rescan unrelated sources, and must not discard durable overrides.
When a repaired entry leaves a filtered list, focus and selection move to a sensible neighbour
rather than to nothing, and the review position survives that.

### Slices

1. **E1 Reason taxonomy.** Split `unavailable` into the distinct states above, with the
   evidence for each read from existing roles rather than a new calculation, and surface the
   reason text the user can act on.
2. **E2 Path repair.** Pick, preview, confirm, with refusals that explain themselves, plus
   undo.
3. **E3 Retry and focus behavior.** Retry scoped to one entry or one selected set, preserved
   focus when entries disappear, and no unrelated rescans.
4. **E4 Desktop, Couch and controller pass.** Small windows, missing drives, offline operation,
   keyboard and controller reachability for every new control.

### Out of scope

A navigation redesign, bulk destructive removal, automatic metadata replacement, cloud
anything, and any action that cannot be completed from the app.

## Sequence and the release boundary

Ranked by value per unit of risk, with the reason:

1. **D, the Dolphin adapter.** Smallest change, no new source and no new emulator, and its
   evidence is already on this machine: `~/.config/dolphin-emu/TimePlayed.ini` holds two real
   disc ids, and Dolphin is an emulator whose games are normally started from its own file
   picker, which is the case that currently falls back to reading a window title.
2. **C, the three sources.** The headline feature and the largest piece. One source per commit,
   melonDS first to establish the pattern. The honest blocker is acceptance: none of the three
   emulators is installed and there is no PS3, PSP or DS content on this machine, so real
   gameplay acceptance needs both.
3. **E, repair actions.** Mostly additive, but path repair is genuinely new persisted state and
   the reason taxonomy needs per-source knowledge that parts C and D produce. It is cheaper
   after C than before it.
4. **B, activity intervals.** Last, and I would ship less of it now. Every one of the 73
   recorded sessions would allocate identically, pause-on-unfocus is off, and there is no
   suspend gap in the data. Persisting intervals (B1) is cheap and makes the later allocation
   switch possible without a second migration; switching the allocator and the labels is the
   part that can move a number the user has already seen, so it is the part worth doing once
   the pause feature has real use.

Recommendation: 1.12 ships D and C, plus E if it lands without delaying C, with B1 only, on
one integration branch. That is a narrowing of the handoff's scope, so it is the maintainer's
call, not a decision to take silently.

   weaker for the release's headline feature.
3. **RPCS3 save attribution.** `SaveLayout` cannot express "read each save directory's own
   PARAM.SFO", so per-game save attribution is either a small resolver hook in the save layer
   or a documented heuristic on the title-id prefix. Recommendation: the resolver hook, because
   the heuristic claims per-game protection that the container does not provide.
4. **Whether the DS/PSP shared save containers may be backed up at all** in their whole form,
   given that a shared container means one game's backup includes other games' data. My
   recommendation: back up per game where the format allows it, label the container shared
   everywhere it appears, and refuse to present a whole-container snapshot as per-game
   protection.
